# M3 Buy Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build guest cart, coupon, COD/bank-transfer checkout, atomic order creation, stock reservations, confirmation, and order tracking on local Supabase.

**Architecture:** Next.js Server Components and Server Actions own request validation, cookies, redirects, and safe UI errors. PostgreSQL RPCs own cart/order writes, money calculations, coupon rules, idempotency, row locks, and stock reservations inside transactions. Raw cart/order tokens stay in httpOnly cookies; only SHA-256 hashes enter PostgreSQL.

**Tech Stack:** Next.js 16 App Router, React 19, strict TypeScript, Supabase JS, PostgreSQL/PLpgSQL, Tailwind CSS v4, Zod, Vitest + React Testing Library, Supabase SQL tests, Playwright MCP browser smoke.

## Global Constraints

- Create `feature/commerce-buy` from current commit `5558b69`. While PR #1 remains open, open M3 as a stacked PR against `feature/catalog-browse`; after PR #1 merges, rebase and retarget M3 to `main`. Do not modify production.
- Use a new migration; never edit `supabase/migrations/202607230001_catalog.sql` or `supabase/migrations/202607230002_catalog_list_view.sql`.
- Add only `zod` as a runtime dependency; use Node/Web Crypto and native React/HTML instead of new cart or form libraries.
- Store money as whole-VND PostgreSQL `numeric`; never calculate order totals with JavaScript floating point.
- Server Actions validate every `FormData` field with Zod; client validation only improves UX.
- PostgreSQL RPCs are the write boundary; anonymous clients get no direct commerce table write grants.
- RPCs use `SECURITY DEFINER`, fixed `search_path`, explicit grants, and safe error codes.
- Cart and order tokens are generated with `crypto.getRandomValues`, hashed before database use, and never logged.
- Transfer reservations expire after 24 hours; COD reservations have no expiry in M3.
- Shipping is always `0` in M3 and must be displayed explicitly.
- Do not claim completion while lint, type-check, unit tests, SQL tests, build, or browser smoke fails.
- Keep existing unrelated working-tree changes (`next-env.d.ts`, `.claude/`, `.codegraph/`, `.playwright-mcp/`, `docs/` files outside this plan) out of feature commits.

- [ ] **Step 4: Add active-reservation calculation**

Create a helper function used by RPCs and catalog reads:

```sql
create function available_variant_stock(p_variant_id uuid)
returns integer
language sql
stable
security invoker
set search_path = public
as $$
  select greatest(
    inv.quantity - inv.reserved_quantity - coalesce((
      select sum(ir.quantity)
      from inventory_reservations ir
      join orders o on o.id = ir.order_id
      where ir.variant_id = p_variant_id
        and ir.released_at is null
        and (ir.expires_at is null or ir.expires_at > now())
        and o.order_status not in ('cancelled', 'expired')
    ), 0),
    0
  )::integer
  from inventory inv
  where inv.variant_id = p_variant_id;
$$;
```

Replace the existing `catalog_products` view in the new migration, preserving its columns and changing only `available_stock` to sum `available_variant_stock(v.id)` across active variants. Re-grant select on the view. Add a detail-query-compatible RPC or update later query fields so product detail uses the same reservation calculation.
